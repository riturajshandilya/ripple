# Ripple

A reconstructed multi-turn assistant with an Alexa adapter and a shared conversation core. Echo → Alexa → HTTPS tunnel → Express → assistant core → Groq (or optional OpenAI). It retains bounded recent session context, stores successful turns and personal memory locally, and can retrieve relevant history and memories. Automatic memories are unverified. A local memory-correction tool can be proposed by Groq and requires confirmation. The Mac push-to-talk client uses local speech models; the user has reported that it works.

The transport-independent orchestration lives in `src/core/assistant.ts`; `src/alexa/skill.ts` translates Alexa requests and speech responses. The core currently retains the six-second Alexa-oriented deadline, so the Mac adapter still needs its own configurable timing and interruption behavior.

For short or referential follow-ups such as “update it,” retrieval also uses up to two preceding user questions as context. This is a bounded heuristic, not full conversational understanding; it can include irrelevant context or miss indirect references. Search remains local, and retrieved excerpts plus the recent conversation are sent to the answer provider.

In the default always-retrieve flow, diagnostics report only elapsed retrieval time, history and memory result counts, and whether each search was complete. They do not include the question, answer, memory text, conversation IDs, or retrieved excerpts. The server writes these metadata to its structured log; the Mac client prints them in its terminal. These counts show what was prepared for the answer call, not whether the model used a particular record correctly. Routed mode does not yet emit this summary.

## Mac dictation development app

The first offline Mac slice is a locally built menu-bar app. Build it using the working nvm Node and run `npm run app:build`, then open `dist/Ripple.app`. This development bundle points back to this project and is ad-hoc signed; it is not an installable, notarized distribution. Choose **Enable Permission** in its bubble. It deep-links to the next missing macOS Privacy & Security pane: Input Monitoring, Accessibility (used for selected text and insertion), then Microphone. Grant that permission, return to Ripple, and click again to open the next missing pane. macOS controls each approval; the app cannot enable permissions itself. These permissions are independent, and the app may need to be relaunched after a grant. Rebuilding can change its ad-hoc signature and macOS may require permissions again. To add it manually in System Settings, choose the app at `dist/Ripple.app`.

In a supported editable field, hold Control + Option, speak, then release the keys. Ripple uses a restrained, progressive-disclosure three-tier desktop interface:

- **Tier 1 (Ambient Liquid Droplet v2)**: A native macOS droplet indicator rendered in SwiftUI `Canvas` inside a pausable `TimelineView`. In resting idle, it sits quietly as a 10pt Obsidian Pearl (`#1C1E26 @ 88%`) at 0.0% CPU. While listening, it expands into an organic amoebic droplet driven by a 3-octave periodic noise field on the unit circle $(S^1 \times \mathbb{R})$ with fluid time drift and low-band quadrupole squash—eliminating spinning turbine effects and boundary seams. Its color dynamically blends from Electric Cyan (`#55D7F2`) to Soft Violet (`#8E6CFF`) on vocal peaks, breathes gently in transcribing, respires harmonically in polishing, flashes Emerald Green (`#34D399`) on success, and wobbles in Coral Red (`#FB7185`) on error. Clicking the droplet opens the **Ripple Hub**.
- **Tier 2 (Compact Whisper Toast)**: A floating 368 × 64 px glass capsule presented only on exceptions (clipboard fallback when no editable field is focused, read-only selection transformations, permission alerts, or errors). It provides one-click **Copy**, a **Details ↗** shortcut into the Hub, and an automatic 6.5s collapse timer.
- **Tier 3 (Ripple Hub Window — Warm Editorial)**: A refined SwiftUI window (minimum size: 560 × 460 px, default: 900 × 580 px) styled with Direction B's warm stone/alabaster surfaces (`#141416` / `#FAF9F6`), Muted Iris accent (`#8B5CF6` / `#6D28D9`), borderless resting cards with hairline selected border only, tri-system typography (SF Pro Rounded headers, SF Pro text with `.monospacedDigit()` for counters/timestamps), and sentence-case headers. Structured into three clean tabs:
  1. **Transcripts (2-Pane Focus Feed + On-Demand Modal Sheet · Option 2)**: A wide, uncluttered 2-pane layout (180pt sidebar + flexible main canvas) showing final formatted text and quiet timestamps grouped chronologically (_Today_, _Yesterday_, _Earlier_), alongside instant search and word count summary. Row hover reveals an isolated one-click **Copy** button (which copies directly without triggering row selection). Clicking the transcript row opens the focused **Dictation Details & Iteration Sheet** (480 × 530 px modal sheet, `Esc` to dismiss):
     - **Result**: Displays the full result with a subtle **Compare Raw** toggle when transformations occurred, revealing a Before (Spoken Raw) → After (Final Result) stacked comparison.
     - **Re-transform**: Allows re-running and refining dictations locally without re-recording.   2. **Style & Language (Streamlined 3-Card Settings · Option 4)**: Consolidates settings into 3 calm, grouped macOS Settings sections:
     - **Default Dictation Mode**: 4-segment control (`Raw | Plain | Email | Code`) with dynamic helper caption explaining the active mode.
     - **Script & Translation**: Grouped card with **Output script** dropdown (`Spoken (Original script)`, `Latin (Romanized) · e.g. Aap kaise ho?`, `Translate`) and **Translate target** selector.

The ◉ menu provides quick profile switching, language selection, and history toggles. Whisper’s detected-language transcript remains the raw source text and is stored separately from the final output in `data/dictations.sqlite`. Raw + original script makes no formatter call; Raw + romanization or translation calls the configured formatter only for that explicit conversion without polishing wording. Polish applies the selected style and output language/script together via the configured formatter chain in `DICTATION_FORMATTER_ORDER` (default: Groq key 1, Groq key 2, OpenRouter free Gemma with key 1, OpenRouter free Gemma with key 2, then local Ollama Qwen 14B offline fallback). If every provider fails, the app returns raw transcription.

The app captures the focused app, field and selection before recording, then rechecks focus before pasting once through the macOS clipboard and Command-V. The transcript replaces the clipboard contents. Ripple does not press Enter, so a pasted terminal command is not executed automatically. If the target is unavailable, read-only, changes before delivery, or rejects the text, Ripple automatically copies the completed output to the clipboard and shows a copy/manual-paste status. If delivery is uncertain, it does not retry Command-V because some text may already have arrived. The bubble's Copy button remains available. Secure fields identified by macOS are rejected, but third-party accessibility metadata is not guaranteed complete. Delivery status records only whether the paste event was sent; it cannot prove the receiving app accepted every character. Temporary audio and transcripts are held in an owner-only temporary directory and normally deleted after each turn; a crash or forced termination may leave them behind. By default new dictations are stored locally in `data/dictations.sqlite`: timestamp, raw and final text, mode, style, output language/script, translation target and formatting status, but no audio. Use the menu to disable history, view the latest 200 records, or delete all history. Storage lasts until deletion; existing dictations from before history was added cannot be recovered here. The database is owner-only but has no separate application-level encryption; use FileVault and encrypted backups as appropriate. Deletion does not erase backups. macOS may not identify every secure field, so avoid dictating secrets. Timing and insertion failure categories (no dictated text or target details) are written to `data/performance.jsonl`.

When you select text and dictate an explicit transformation request such as “transform this into a structured email,” Ripple reads only the selected text through Accessibility and passes it separately from your spoken instruction to the configured formatter chain. In editable fields it replaces the original selection after confirming focus and selection are unchanged. For selectable read-only text such as Terminal scrollback, it shows a copyable transformed result and never pastes into the shell or executes anything. This requires the app to expose selected text and range through macOS Accessibility; some terminal views may not, in which case Ripple stops without changing anything. A missing selection or formatter failure leaves the original selection untouched; it never pastes the command as a fallback. The selected source text is not stored in dictation history, but the spoken instruction and transformed output follow the existing history setting. Cloud formatting sends both the selected text and spoken instruction to the configured provider. Selection input is capped at 12,000 UTF-16 code units. Ordinary dictation continues to replace the selection with the dictated transcript when a selection is present.

The proposed history, notes, opt-in Drive sync and iOS architecture is in [dictation-design.md](docs/dictation-design.md); controlled test results are in [dictation-feasibility.md](docs/dictation-feasibility.md). The user verified selection transformation in Notes; this build adds copy-only support for readable selections in read-only fields such as Terminal. Actual Terminal Accessibility behavior still needs a device check. Notes, Google OAuth, sync, iOS app, and streaming transcription are not implemented; cloud formatting is implemented through the configured provider chain. `npm run test:mac-focus` opens a temporary AppKit test window to check selected-text capture and stale-target rejection; it checks a synthetic read-only selection as well as stale-target rejection, but does not verify Command-V delivery in every app. `npm run test:mac-browser` opens a disposable Chrome profile and synthetic local page.

## Mac push-to-talk prototype

Run `npm run build` and `npm run voice` from the project directory using the working nvm Node version. With voice mode running, hold Control + Option to record and release either key to finish. Hold the keys for at least a quarter of a second; recording stops automatically after 45 seconds. Wait until the response finishes before starting another turn. Press Ctrl-C in the terminal to exit. This is push-to-talk: it cannot interrupt playback or listen continuously.

The shortcut is global while voice mode runs, even when the terminal is in the background. It uses a passive macOS listener for modifier changes only; it does not consume keys or collect typed text. Control + Option can also be used by other macOS apps, including VoiceOver, so those shortcuts may trigger recording. macOS may request Input Monitoring for Python or its host application at startup and microphone access on the first hold. If denied, enable the relevant application in System Settings → Privacy & Security → Input Monitoring and Microphone, then restart voice mode. Voice mode does not start automatically on login.

Whisper.cpp `small` transcribes locally with automatic language detection, the shared assistant core retrieves context from the existing SQLite history and sends the transcript and any selected context to the configured provider, and Mithi generates speech locally. The speech processes do not receive provider credentials. Successful turns are stored in the existing conversation database, subject to the existing retention and privacy policies. Automatic memory extraction and background indexing are performed by the existing backend workers; if the Alexa backend is not running, jobs wait until it starts. Running both processes means they share SQLite, and a database write failure is reported without retrying the turn.

For Mithi, a Devanagari character selects Hindi; otherwise it selects English. This is only a script heuristic, so Romanized Hindi and mixed-language pronunciation may be wrong. Emotion controls, full-duplex interruption, accurate language selection and Mac control are not implemented. Audio and transcripts are held temporarily in an owner-only temporary directory and removed after each turn and on normal exit or Ctrl-C; an abrupt crash or forced termination can leave files in the system temporary directory. Neither the transcript nor generated answer is printed by the voice client. Inference loads Mithi for every turn, so the prototype can be slow.

On this Mac the dependencies are already installed. To recreate them, install Homebrew's `whisper-cpp` and `portaudio`, and use Python 3.13 and `uv` to create `.voice-venv`. Install `scripts/voice/requirements.lock` into that environment, download `ggml-small.bin` from the [whisper.cpp models repository](https://huggingface.co/ggerganov/whisper.cpp) into `.voice-models/`, and download [Mithi](https://huggingface.co/Oomni/mithi-v1-flash) into `.voice-models/mithi/`. This installation used Mithi revision `9dd0cb4fb4b4ab78849993e15a80488d05c34821` and Whisper model repository revision `5359861c739e955e79d9a303bcbc70fb988958b1`. Model files, dependencies and local data are Git-ignored. Review source and licenses before installing on another machine.

## Voice timing diagnostics

The Mac client writes content-free timing events to `data/performance.jsonl` (owner-only; rotated after approximately 1 MB). Events contain a timestamp, stage, duration, success and, for retrieval, counts and completeness flags. They never contain recognized text, model output, memory content or credentials. Stages include recorded audio length, transcription, retrieval, provider call, overall assistant processing, speech synthesis and playback. Retrieval and provider are parts of assistant processing, so do not add all durations together. Playback duration reflects how long the audio played, not processing latency. This logging currently applies to the Mac client and default always-retrieve provider path; routed mode lacks the provider timing event. `tail -f data/performance.jsonl` shows metrics after a turn.

The configured Groq model is `openai/gpt-oss-120b` for a trial; edit `GROQ_MODEL` in `.env` and restart the processes to revert to `openai/gpt-oss-20b`. This setting also affects automatic memory extraction. Confirm the Groq account and current free-tier limits before live comparisons. `scripts/compare-groq-voice.ts` sends eight synthetic prompts to Groq and consumes provider quota; it does not read private memories or history.

## Alexa and tunnel

Install Cloudflare's `cloudflared` when ready, then run `cloudflared tunnel --url http://127.0.0.1:3000`. A Quick Tunnel URL changes after restart and exposes both `/health` and `/alexa`; it is not route-restricted. In the existing Alexa developer console skill, set its HTTPS endpoint to the new URL plus `/alexa`, choose the certificate option for a wildcard certificate from a certificate authority, and confirm the skill and Echo use English (US). Check the actual invocation name and model in the console before making changes; `skill/en-US.json` contains proposed additional natural question intents; the previously shared console model does not yet include them. Build the model if changed. Test in the simulator, then on the Echo with the required carrier phrase, e.g. “Alexa, ask test assistant to ask what is Redis.” Actual recognition needs device testing.

The ASK Express adapter verifies signatures and timestamps, and the SDK validates the configured skill ID. Do not add a body parser before the adapter. The provider has a 5.5 second timeout and no retries. Amazon documents an eight-second full-response window, so network and Alexa overhead also matter. See [Amazon's adapter documentation](https://developer.amazon.com/en-US/docs/alexa/alexa-skills-kit-sdk-for-nodejs/host-web-service.html) and [response timing](https://developer.amazon.com/en-US/docs/alexa/custom-skills/progressive-response-api-reference.html). Groq uses its [OpenAI-compatible endpoint](https://console.groq.com/docs/openai).

Conversations are held in process memory for up to 10 minutes of inactivity (cleaned on subsequent access), with a maximum of 100 sessions and five recent turns per session. Stop and session end clear a session; restarting the server clears all sessions. Up to four previous turns and the current question are sent to the provider. Successful questions and answers are also stored in `data/history.sqlite` for inspection, with relevant excerpts retrieved on each question in the default always-retrieve mode. The database and journal are inside a Git-ignored directory; the database file is owner-only. FileVault was on when checked, but no Time Machine destinations were configured. The database is not separately encrypted: protect the Mac account and use an encrypted backup if you configure one. Deleting a conversation from SQLite does not delete existing backups or guarantee forensic erasure from storage. The model provider receives each question; check its current data handling and account settings.

## Conversation history

Each successful turn is stored as a user message and an assistant message in one SQLite transaction. Conversation IDs are local random IDs; Alexa session IDs are hashed for grouping. Failed provider calls are not stored. By default, conversations inactive for 30 days are deleted on application or history-command startup and when a new turn is saved; this is not a background timer. Change `HISTORY_RETENTION_DAYS` in `.env` to an integer from 1 to 3650. This retention also applies when running the commands below.

```sh
npm run build
npm run history -- list
npm run history -- show <conversation-id>
npm run history -- delete <conversation-id>
```

`show` prints private conversation content to your terminal. Deletion removes the conversation and its messages from the active database, but not copies or backups. If the same Alexa session continues after deletion, new turns can create a new conversation. If saving fails, the assistant still answers and the server logs a generic error; the unsaved turn cannot be recovered from history.

## Search history

Run `npm run history -- search redis cache` to search saved messages locally. The results include a conversation ID, role, timestamp, and a short snippet with matches in brackets; snippets may contain private conversation content. Search returns up to ten ranked message matches, and every supplied word must occur in the same message. Searches are case-insensitive word matches, not semantic search or exact phrase matching. Input is limited to 200 characters and 12 words; punctuation separates words and search operators are treated as ordinary words.

SQLite FTS5 keeps a word index inside the same database and automatically indexes saved messages. Existing history is indexed when the schema is upgraded. Deleting a conversation or applying retention removes its messages from search results. The index may retain recoverable traces at the storage level, and deletion does not erase backups. In the default always-retrieve mode, each question can search history and matching excerpts can be sent to the configured model provider.

## Asking about previous conversations

Say “Alexa, ask test assistant to ask what did we talk about regarding the Indian population?” In the optional `ANSWER_FLOW=routed` mode an LLM router chooses direct answering, history search, or clarification based on the latest question and up to four recent messages. The default `always_retrieve` mode searches for every question and makes one answer call. The router can misclassify questions or choose poor search terms. In routed mode, set `HISTORY_ROUTER=rules` in `.env` and restart to use the original phrase-based router. Search requires all extracted words in the same message, so try a short topic if it misses. It selects up to four matching messages and nearby turns, with bounded excerpts, and sends them to the configured provider with the question. Saved content is untrusted and the model is instructed to treat it as evidence, not instructions. This is not a guarantee against prompt injection or incorrect answers. No match returns a local response without calling the model.

## Router evaluation

`npm run eval:router` sends six synthetic examples to the configured LLM provider and compares its route with the original rules. This makes live API calls and uses the account’s limits. It never reads the history database. Routing receives up to five recent messages (including the current question), truncated to 500 characters each; it therefore sends that context to the configured provider. Search is local, but matching excerpts are sent to the provider for the answer. A route or provider failure returns a generic response rather than silently guessing. In routed mode, each voice turn generally uses two model calls. The default always-retrieve mode uses one answer call; optional background extraction still makes an additional call.

## Voice responses and interruption

The answer prompt asks for brief speech-ready plain text without Markdown or SSML, including for history answers. Model compliance is not guaranteed; model text is escaped before the SDK wraps it in SSML. Amazon supports wake-word interruption while Alexa speaks; say “Alexa” followed by the next request, or say “Alexa, stop” to stop. Stop ends this skill session. Whether an interrupted follow-up remains in the same session depends on Alexa behavior and needs Echo testing. The backend stores the whole generated answer, even if playback was interrupted; it cannot tell how much was heard.

The local `skill/en-US.json` proposes `what is`, `what are`, `what about`, `how many`, and `did we talk about` intents. Their carrier words are restored in the backend question. To test them, copy the local JSON into the developer console JSON editor, save and build the English (US) model; review the existing model first and preserve any other edits. Alexa requires a carrier phrase for SearchQuery utterances; this does not support unlimited prefix-free speech. The model build, recognition, wake-word interruption and voice quality require real-device verification.

The local candidate model also includes `do you remember {question}` and `do you remember`. The backend sends the reconstructed wording and recent session context to the router; if no slot was captured, it asks for a topic. A vague phrase such as “about this” may still need clarification or be misrouted. This intent must be built in the Alexa developer console before device testing.

The candidate model includes additional natural openings such as “can you,” “could you,” “would you like,” “do you know,” “how does,” and “why is.” The backend restores the selected intent's opening before routing; it cannot recover the actual spoken words if Alexa selects the wrong intent. A local handler test does not verify recognition. After building the model, use the Alexa simulator and Utterance Profiler to inspect the intent and slot, then try the same conversation on the Echo. Similar samples can overlap, and arbitrary wording is not guaranteed to work.

The local candidate model now has 138 distinct carrier-phrase samples, with 140 intents and 135 slot declarations. The 108 generated carriers are listed in `skill/additional-carriers.json`; after edits, run `npm run model:generate`, then build and test the resulting model in Alexa. The model and backend must be deployed together. Many patterns overlap, and a local test only checks reconstruction after an intent is selected—not Alexa's recognition or model acceptance. Export or review the current console model before replacing it so unrelated console changes are preserved.

The backend temporarily retains mappings for removed intents from the previous candidate model, so an already-built older model can continue to send them. The current candidate has 275 intent plus slot declarations under a conservative combined count; Alexa documents a separate 350 limit for intents plus custom slot types. Shorter carriers may recognize longer phrases, but coverage needs device testing.

## Personal memory experiment

In the default `always_retrieve` flow with Groq, the model can propose `propose_memory_update` when the user asks to correct a retrieved memory. The backend validates the proposal against retrieved IDs, fetches all records with the same exact topic, and describes their existing values and the proposed new value. Say “yes,” “update it,” or “no” on the next turn. The database changes only after explicit confirmation; the app rechecks the reviewed snapshot and cancels if it changed. Same-topic duplicates are merged into one record and their previous values and existing revisions are retained in its revision history. The review is limited to five records and 600 characters. Pending actions are session-local, expire after two minutes, disappear on restart or session end, and are not persisted. If the user says something other than an unambiguous confirmation or cancellation, the proposal is discarded without a change and the new utterance is processed as a new request. The proposed new value must occur in the current transcript, so the model cannot silently reuse an old value. This conservative check may ask for clarification even when the intent is clear. Recognition and model selection can still fail; model proposals are not proof of the user's intent. A normal preference statement that is not recognized as a tool proposal may still be saved separately by the existing automatic extractor.

As a deterministic alternative, say “update memory for exercise to 45 minute workouts”; the topic must match exactly (case-insensitively), and the same review and confirmation applies. The explicit command itself does not call an LLM. Alexa must recognize and forward the request; the local interaction model adds `AMAZON.YesIntent` and `AMAZON.NoIntent`, which must be built in the developer console before those replies can be tested. A session can also end before confirmation. Tool calling is currently enabled only for Groq in the default always-retrieve mode; optional OpenAI and routed mode retain the answer-only provider flow. Check exact topics with `npm run memory -- list` (this prints personal data locally).

Personal memories are separate from conversation history. Automatic extraction is enabled by default for most new successfully saved turns; tool-proposal and confirmation turns are excluded. Eligible turns are sent to the configured LLM in a background job, and proposed explicit facts are stored with `automatic_unverified` provenance and the source message ID. The model has made false positives in tests; these records may be wrong or attributed to the wrong speaker. The backend checks the source quote and fields but cannot prove truth. Automatic correction candidates are saved separately and do not overwrite older memories. Confirmed corrections group records by exact topic and preserve previous values in a revision table; these revisions are deleted with the memory. A pending automatic extraction cannot overwrite or recreate a manually corrected exact topic, but differently named topics can still conflict.

```sh
npm run memory -- add
npm run memory -- list
npm run memory -- search
npm run memory -- update <memory-id>
npm run memory -- revisions <memory-id>
npm run memory -- delete <memory-id>
```

Add, update and search prompt for input rather than placing the content in the shell command. Listing and searching print potentially sensitive content to the terminal. `search` is a basic bounded keyword lookup that matches any term and returns at most three results; a match is a candidate, not proof of relevance. The memory table and its FTS index live in `data/history.sqlite`, protected by the same file permissions and Git ignore as history. Memories remain until explicitly deleted, independently of the conversation history retention setting. Deletion does not remove backups or guarantee physical erasure; deleting conversation history does not delete memories.

`npm run eval:memory` sends four synthetic questions to the configured model to experiment with a separate decision to search, skip, or clarify. It does not read real memories and incurs provider usage. The decision is not used in live Alexa traffic. Model routing, candidate relevance, latency, privacy, and prompt injection need further evaluation before automatically sending memories to the provider.

## Extraction-only evaluation

`npm run eval:extraction` sends eight **synthetic** example conversations to the configured model and prints candidate fields, an expected-versus-observed count and elapsed time. It uses provider quota; it does not read real conversation history or write memories. Do not add private conversations to the checked-in evaluation cases. Candidate validation checks structure, bounds and whether `source_text` is an exact substring of the current user message. This does not establish that a statement is about the user, true, durable, or safe to store. Candidate content and correction labels require manual review. The synthetic evaluator itself remains isolated from Alexa and does not write memories; the separate background worker uses the same extractor for new Alexa turns.

## Automatic and semantic memory

`AUTO_MEMORY_ENABLED=true` (default) enqueues extraction after most successfully saved turns from either adapter; tool-proposal and confirmation turns are excluded. Set it to `false` in `.env` and restart to stop enqueuing and processing; existing memories remain. Jobs persist in SQLite, retry up to three times, and `npm run memory -- status` reports counts without message content. Previously saved conversations are not backfilled. The user message and bounded nearby context are sent to the configured provider for extraction; each job is an extra API call. Failed jobs remain failed and are not automatically retried after three attempts. Automatic memories are unverified and are not silently used to overwrite existing records; duplicate exact topic/content pairs are skipped. Conversation retention or deletion can remove a source message, leaving the memory and a null source reference. Removing a memory does not remove past source text or backups.

Local Ollama with `nomic-embed-text:latest` generates numerical vectors for memory records and questions. Vectors and content hashes are stored in the same SQLite database. Each query compares at most the most recently updated 500 memories by cosine similarity using a linear scan, not a vector index. In default mode, up to two memories are supplied to the answer model using vector matches above the experimental 0.65 threshold and literal FTS matches; literal matches do not use the vector threshold. This threshold is not calibrated and can miss relevant memories or send irrelevant ones. A lookup runs on each supported Alexa question; the locally retrieved memory, when selected, is sent to the configured answer provider and labeled unverified. The shared retrieval step has an approximately 1.8-second budget; cold model startup was observed to be slower. A background synthetic warmup runs at startup, but misses and model unavailability remain possible. If the lookup is unavailable, the answer model is informed; the model may still respond incorrectly. `npm run memory -- semantic` offers interactive local search, and `npm run eval:semantic` tests synthetic data. Semantic vectors are invalidated on content changes, and deleted with their memory. If the Ollama model behind the `latest` tag changes, cached vectors should be rebuilt; model-version pinning and reindex tooling are not yet implemented.

## Architecture diagram

[End-to-end Mermaid flow](docs/ripple-flow.mmd) shows Alexa request handling, session context, personal-memory extraction and retrieval, and hybrid conversation-history retrieval. The diagram describes the implementation, including its bounded searches and fallbacks.

Conversation-history retrieval now combines SQLite FTS5 keyword matches with semantic similarity over the 500 newest messages. A local background worker indexes messages in batches; embeddings are cached in SQLite and deleted with their source messages. The semantic component uses Ollama on the Mac, a 0.65 experimental cosine threshold, and a linear scan. The two ranked lists are combined using reciprocal rank fusion and nearby turns are included. Keyword search can still find older records. The answer model receives a completeness flag if vector indexing is incomplete or unavailable; it may still fail to report this accurately. For local inspection, run `npm run history -- semantic` and enter a query at the prompt; it prints private excerpts. `npm run eval:history-semantic` uses only synthetic in-memory data.

## Always-retrieve answer flow

The default `ANSWER_FLOW=always_retrieve` skips the separate history-classification LLM call. The local embedding service generates one query vector, and the same vector searches SQLite `sqlite-vec` history and memory tables. SQL nearest-neighbor queries apply cosine distance `<= 0.35` (equivalent to similarity `>= 0.65`) and return at most ten history hits and three memory hits, before application-side selection. The independent FTS keyword path may return items below that vector threshold. The native `sqlite-vec` implementation used here scans candidate vectors in SQLite; it is not an approximate nearest-neighbor index, and it does not guarantee sublinear search. It avoids loading all vectors into Node. Existing JSON vectors are backfilled during schema migration and synchronized by triggers. Both semantic searches cover only the 500 most recent records of each kind.

The backend includes up to two history conversations with nearby bounded turns, up to two personal memories, and retrieval coverage status in one answer LLM call. It tells the model to treat retrieved records as untrusted and use only relevant context. A separate LLM extraction call still runs in the background when automatic memory is enabled. The short semantic timeout, experimental threshold, approximate model-generated answers, keyword false positives, 500-record cap, and mutable embedding model tag can all affect results. No model is guaranteed to ignore malicious stored instructions. If search is incomplete or unavailable, the answering model is informed; fallback behavior remains model-dependent.

Set `ANSWER_FLOW=routed` and restart to restore the prior classifier-first path (`HISTORY_ROUTER` chooses its router). `npm run eval:always` exercises retrieval on synthetic data only; it does not read personal records. The `sqlite-vec` dependency is pre-1.0 and pinned by the lockfile; it needs a compatible platform binary for SQLite to open this database.
